# Kinolike — логика приложения

Документ описывает фактическую логику текущей реализации. Основные точки входа:

- frontend: `src/main.tsx` (собирается Vite в `client/`);
- backend: `server/index.js`;
- база данных: `server/db/schema.sql` и миграции в `server/db/migrations/`.

## 1. Назначение и архитектура

Kinolike — одностраничное веб-приложение для поиска фильмов и сериалов, ведения пользовательских списков, выставления оценок и получения рекомендаций.

```text
Браузер
  └─ React/Vite SPA
       └─ API /api/* (Express)
            ├─ PostgreSQL — пользователи, списки, метаданные, кэш
            ├─ TMDB — каталог и метаданные
            ├─ OpenAI-compatible API — анализ естественных запросов
            ├─ Jackett → TorrServer — поиск и получение торрентов
            └─ Jellyfin — библиотека и внешние ссылки на просмотр
```

Frontend собирается Vite и использует React Router с URL-маршрутами `/watched` и `/movie/123`.

## 2. Запуск сервера

`server/index.js` выполняет следующие действия:

1. Загружает `.env`.
2. Создаёт Express-приложение.
3. Подключает security-заголовки через Helmet, CORS с credentials и общий rate limit для `/api/`.
4. Включает разбор JSON-запросов с лимитом 10 MB и URL-encoded данных.
5. Раздаёт статические файлы из `client/`.
6. Подключает API-маршруты.
7. Для любого не-API пути возвращает `client/index.html`, чтобы React Router продолжал работать после прямого открытия URL.
8. Инициализирует PostgreSQL-схему и последовательно применяет SQL-миграции.
9. После успешной инициализации запускает HTTP-сервер на `PORT` (по умолчанию `3000`).

Ошибка необработанного запроса преобразуется в HTTP 500 с сообщением `Ошибка сервера`.

## 3. Жизненный цикл frontend

После запуска React-приложения инициализируется `AuthProvider`:

1. Выполняется `GET /api/auth/me`; при успехе используется существующий пользователь PostgreSQL.
2. JWT из `localStorage` автоматически добавляется к API-запросам, cookie передаётся через `credentials: include`.
3. Публичным остаётся каталог и поиск; списки, детали, рекомендации и профиль требуют авторизации.
4. Данные страниц загружаются React-компонентами напрямую из `/api/*`, без mock-данных.

`API.request()` добавляет JSON-заголовки, Bearer-токен из `localStorage`, cookie credentials и преобразует ошибки backend в JavaScript `Error`. При ответе `401 INVALID_TOKEN` токен из `localStorage` удаляется.

### Маршруты SPA

| URL | Обработчик | Авторизация |
|---|---|---|
| `/` | каталог `HomePage` | нет |
| `/want` | список `ListPage` (`want_to_watch`) | да |
| `/watching` | список `ListPage` (`watching`) | да |
| `/onhold` | список `ListPage` (`on_hold`) | да |
| `/watched` | просмотренные `ListPage` | да |
| `/recommendations` | рекомендации `RecommendationsPage` | да |
| `/movie/:id` | детали фильма `DetailPage` | да |
| `/tv/:id` | детали сериала `DetailPage` | да |
| `/person/:id` | фильмы и сериалы персоны `PersonPage` | да |
| `/login` | форма входа | нет |
| `/register` | форма регистрации | нет |
| `/profile` | профиль и статистика `ProfilePage` | да |
| `/search?q=...` | поиск через TMDB | нет |

Если защищённый маршрут открывается без пользователя, приложение переводит на `/login` с сохранением адреса. Неизвестный путь отображается как 404.

## 4. Аутентификация

### Регистрация

`POST /api/auth/register` проверяет обязательные поля, длину пароля от 6 символов, уникальность email и username. Пароль хэшируется через bcrypt, создаётся пользователь и JWT со сроком жизни 7 дней. JWT возвращается в JSON и записывается в httpOnly cookie `token`; frontend также сохраняет возвращённый токен в `localStorage`.

### Вход и выход

- `POST /api/auth/login` проверяет email и пароль, создаёт JWT и возвращает публичные данные пользователя.
- `POST /api/auth/logout` очищает cookie.
- `GET /api/auth/me` возвращает текущего пользователя.
- `PUT /api/auth/profile` меняет username, email и avatar URL с проверкой уникальности.
- `PUT /api/auth/password` проверяет текущий пароль и сохраняет новый bcrypt-хэш.

Защищённые маршруты принимают токен из `Authorization: Bearer ...` или cookie. Bearer имеет приоритет над cookie. Невалидный JWT очищает cookie и возвращает `401` с кодом `INVALID_TOKEN`.

## 5. Пользовательские списки

Основная сущность — строка `user_lists`, уникальная для пары `(user_id, tmdb_id, media_type)`.

Допустимые статусы:

- `want_to_watch` — хочу посмотреть;
- `watching` — смотрю;
- `watched` — просмотрено;
- `on_hold` — отложено;
- `not_interested` — не интересно.

Дополнительно хранятся оценка `rating` от 1 до 10, заметка, даты добавления/изменения и дата просмотра.

### Добавление и изменение

`POST /api/lists` добавляет фильм или сериал. Если такая пара TMDB ID и типа уже существует, новая запись не создаётся: у существующей записи обновляется статус.

После добавления запускается фоновая предзагрузка метаданных. Метаданные сначала ищутся в `media_metadata`, а при отсутствии загружаются из TMDB.

`PUT /api/lists/:id` позволяет менять статус, оценку, заметку и `watched_at`. Backend проверяет принадлежность записи пользователю. При изменении статуса или оценки планируется обновление рекомендаций.

`DELETE /api/lists/:id` удаляет только запись текущего пользователя и планирует обновление рекомендаций.

### Переход в просмотренные

В интерфейсе списка «Хочу посмотреть» кнопка «Просмотрено» открывает модальное окно. Пользователь может указать оценку и заметку; frontend отправляет статус `watched` и текущую дату в `watched_at`.

На странице деталей кнопки статусов работают как toggle: активный статус повторным нажатием удаляет запись. Для статуса `watched` используется то же окно оценки.

### Экспорт и импорт

- `GET /api/lists/export` возвращает все записи текущего пользователя.
- `POST /api/lists/import` принимает массив `items`, в транзакции удаляет прежние списки пользователя и вставляет импортированные записи.

Импорт поддерживает значения по умолчанию для статуса, оценки, заметки и дат. После импорта планируется пересчёт рекомендаций.

Страницы `watching` и `on_hold` подключены к SPA-роутеру и используют тот же набор фильтров и действий, что и основной список.

## 6. Каталог, поиск и детали

### Главная страница

`HomePage` параллельно загружает:

- тренды фильмов и сериалов за неделю;
- фильмы, идущие в кино в регионе RU;
- будущие релизы;
- топ фильмов.

На странице формируются hero-блок трендов и горизонтальные подборки. Для авторизованного пользователя добавляется раздел «Из вашего списка» из списка `want_to_watch`. Независимые подборки появляются по мере загрузки и не блокируют первый экран.

### Обычный поиск

Верхний поиск открывает `/search?q=...`. Страница вызывает `GET /api/tmdb/search`, поддерживает типы movie/tv/multi, фильтрацию по типу и году, сортировку и дозагрузку страниц.

Поиск в шапке имеет debounce 300 мс и показывает до 8 подсказок. Выбор подсказки открывает соответствующую карточку.

### Детали

`DetailPage` загружает данные фильма или сериала, включая credits, similar и keywords. На странице отображаются:

- backdrop и постер;
- название, год, рейтинг, жанры и описание;
- режиссёр или создатели сериала;
- актёрский состав;
- трейлер;
- похожие тайтлы;
- кнопки статусов пользователя;
- источники просмотра и сохранённые streaming-ссылки.

Клик по актёру открывает данные персоны и её фильмы/сериалы. Кнопка обновления удаляет сохранённые метаданные, после чего страница загружает их заново.

## 7. TMDB и кэширование

`server/services/tmdb.js` — единая обёртка над TMDB API v3.

Логика запроса:

1. Параметры сортируются и хэшируются MD5.
2. По паре `endpoint + params_hash` проверяется таблица `tmdb_cache`.
3. При cache miss выполняется запрос к TMDB с `language=ru-RU` и API key.
4. Сетевые ошибки повторяются до 3 раз с задержкой 2 секунды.
5. Ответ сохраняется в кэш.

Для обычных запросов кэш практически бессрочный. Для динамических данных заданы TTL: тренды — 6 часов, now playing/upcoming — 24 часа, top rated — 7 дней.

Подробные карточки фильмов и сериалов дополнительно сохраняются в `media_metadata` навсегда. В таблице сохраняется исходный JSON и нормализованные поля: год, название, постер, описание, жанры, режиссёры/создатели и до 15 актёров. Списки и рекомендации получают эти данные одним SQL-запросом, без отдельного HTTP-запроса для каждой карточки.

TMDB image proxy `GET /api/tmdb/image` кэширует изображения локально в `server/cache/images` и поддерживает SOCKS5-прокси, если `TMDB_PROXY_ENABLED=true`.

## 8. Рекомендации

В приложении есть три независимых механизма: персональные рекомендации, жанровые подборки и AI-поиск по естественному запросу.

### Персональные рекомендации

Рекомендации строятся только по просмотренным фильмам с оценками. Минимум — 2 оценённых фильма. Сериалы в фоновый персональный алгоритм не попадают.

После изменения списка или оценки вызывается `scheduleGeneration(userId)`. Он объединяет частые изменения debounce-таймером (по умолчанию 1500 мс) и не запускает две генерации одного пользователя одновременно.

Процесс генерации:

1. Из списка пользователя строится профиль по оценённым фильмам.
2. Кандидаты собираются из похожих фильмов высоко оценённых тайтлов, TMDB Discover по любимым жанрам и ключевым словам, а затем при необходимости из top rated.
3. Удаляются все тайтлы, уже присутствующие в списках пользователя.
4. Для кандидатов загружаются подробные метаданные.
5. Кандидаты отбрасываются без жанров и с количеством голосов TMDB менее 20.
6. Каждому кандидату рассчитывается score от 0 до 100 и текстовая причина.
7. Применяется диверсификация: максимум 3 тайтла с одним основным жанром и максимум 1 тайтл одного режиссёра после заполнения половины результата.
8. Результаты сохраняются в `recommendations` с TTL из `RECOMMENDATIONS_CACHE_TTL` или 24 часа.

Вес оценки пользователя:

| Оценка | Вес |
|---:|---:|
| 10 | 5 |
| 9 | 4 |
| 8 | 3 |
| 7 | 2 |
| 6 | 1 |
| 5 | 0 |
| 4 | -1 |
| 3 | -2 |
| 2 | -3 |
| 1 | -4 |

Профиль учитывает жанры, keywords, режиссёров, описание, актёров, страны, языки и десятилетие. Сходство считается через взвешенный Jaccard для этих признаков. Итоговая базовая формула:

```text
score = clamp(50 + weighted_sum × 50, 0, 100)
weighted_sum = Σ(feature_preference × feature_weight)
              + similarity × 0.125
              + quality × 0.05
```

Весовые коэффициенты признаков: genres 0.25, keywords 0.25, directors 0.15, overview 0.15, actors 0.10, countries 0.025, languages 0.015, eras 0.01, quality 0.05. Качество объединяет рейтинг TMDB и количество голосов.

### API рекомендаций

- `GET /api/recommendations` отдаёт действующий кэш; если кэш пуст, запускает генерацию в фоне и возвращает `pending: true`.
- `GET /api/recommendations?refresh=true` принудительно пересчитывает рекомендации.
- `POST /api/recommendations/generate` делает то же принудительно.
- `DELETE /api/recommendations/cache` очищает кэш.

Из кэшированных результатов основной блок отдаёт фильмы. Сериалы показываются в жанровых подборках.

### Жанровые подборки

`GET /api/recommendations/genres` запрашивает наборы TMDB Discover по жанрам фильмов и сериалов. Просмотренные и добавленные в `want_to_watch` тайтлы исключаются. При наличии профиля каждый результат дополнительно получает персональный score и reason; при отсутствии достаточного профиля используется порядок TMDB.

`GET /api/recommendations/favorite-genre` ищет жанр с максимальной средней оценкой пользователя, учитывая только жанры минимум из двух оценённых тайтлов, и строит подборку из TMDB Discover. Просмотренные и уже добавленные тайтлы исключаются.

### AI-поиск

`POST /api/recommendations/search` принимает естественный запрос длиной до 500 символов. Pipeline:

```text
parse_user_request
  → findReferenceMovie (для «похожее на ...»)
  → searchWithRelaxation
  → build_user_profile_data
  → rank_candidates
  → apply_diversity
  → LLM rerank top-N
  → generate_recommendation_reasons
```

LLM преобразует запрос в жанры, исключённые жанры, keywords, настроение, годы, страну, язык и тип запроса. JSON проходит валидацию: жанры сверяются с допустимыми TMDB ID, годы нормализуются, диапазон при необходимости переворачивается, ISO-коды проверяются.

Кандидаты выбираются из локально сохранённых `media_metadata`, поэтому AI не может добавить в результат выдуманный TMDB ID. Учитываются:

- соответствие запросу;
- соответствие личному профилю;
- сходство с высоко оценёнными фильмами;
- сходство с низко оценёнными фильмами со штрафом;
- качество по рейтингу и количеству голосов TMDB.

Итоговые веса: query match 0.40, personal match адаптивно от 0.02 до 0.35, positive similarity 0.15, negative similarity -0.10, quality 0.05. Если AI недоступен или возвращает некорректный JSON, используется fallback-парсер русскоязычных жанров, годов, настроений и выражения «похожее на».

Если результатов мало, сначала снимается ограничение по годам. Для запроса «похожее на» дополнительно используются похожие ID исходного тайтла и ключевые слова.

## 9. Статистика и профиль

`GET /api/stats/overview` возвращает общее количество записей, количество по каждому статусу, среднюю оценку и распределение оценок.

`GET /api/watched/stats` возвращает количество просмотренных всего, отдельно фильмов и сериалов, среднюю оценку и распределение оценок.

На странице профиля доступны:

- отображение пользователя и аватара;
- статистика;
- смена темы;
- смена пароля;
- экспорт и импорт JSON.

## 11. Источники просмотра и стриминг

### Jackett и TorrServer

`POST /api/streaming/search` ищет торренты через Jackett. При пустом результате повторяет поиск без года и по укороченному названию.

`POST /api/streaming/play`:

1. Добавляет magnet-ссылку в TorrServer.
2. Ждёт, пока TorrServer прочитает метаданные и вернёт список файлов.
3. Получает hash и строит ссылки `/stream?link=...&index=...&play`.
4. Для фильма создаёт один `.strm`-файл, для сериала распознаёт сезон/эпизод по шаблонам `S01E01`, `Season 01/Episode 01`, `[01]` или `01.mkv` и создаёт структуру `.strm` по сезонам.
5. Запускает сканирование Jellyfin и ждёт появления элемента, чтобы вернуть ссылку на просмотр в Jellyfin.
6. При наличии пользователя сохраняет ссылку в `streaming_links`.

Выбор результата Jackett добавляет выбранный magnet в TorrServer. После завершения подготовки `.strm` пользователю показывается внешняя ссылка «Смотреть в Jellyfin». Если Jellyfin ещё не успел увидеть файл, доступна повторная кнопка «Найти в Jellyfin».

`GET /api/streaming/link/:type/:tmdbId` возвращает сохранённую ссылку текущего пользователя. `DELETE` удаляет её. `POST /api/streaming/refresh-jellyfin/:type/:tmdbId` повторно сканирует Jellyfin и обновляет `jellyfin_url`. `GET /api/streaming/status` проверяет доступность TorrServer и Jellyfin.

## 12. Структура базы данных

| Таблица | Назначение |
|---|---|
| `users` | учётные записи и хэши паролей |
| `user_lists` | списки, статусы, оценки и заметки |
| `recommendations` | персональный кэш рекомендаций с TTL |
| `streaming_links` | пользовательские TorrServer/Jellyfin-ссылки |
| `tmdb_cache` | кэш ответов TMDB по endpoint и хэшу параметров |
| `media_metadata` | постоянные подробные метаданные TMDB |
| `genres` | справочник жанров TMDB |
| `media_genres` | связь метаданных с жанрами |
| `media_directors` | режиссёры и создатели сериалов |
| `media_actors` | актёры, персонажи и порядок в касте |

Внешние ключи пользовательских данных используют `ON DELETE CASCADE`. Для пользовательских списков, рекомендаций и streaming-ссылок действуют уникальные ограничения, предотвращающие дубли.

## 14. Особенности текущей реализации

- `SPEC.md` описывает более раннюю архитектуру на SQLite; фактический код использует PostgreSQL и `pg`.
- В таблице и API поддерживаются `watching`, `on_hold` и `not_interested`; первые два статуса доступны отдельными frontend-страницами.
- Основной кэш персональных рекомендаций отдаёт фильмы; сериалы формируются отдельными жанровыми подборками.
- В `POST /api/recommendations/custom` проверяется поле `query`, но текущая вспомогательная функция генерации не передаёт этот query в персональный алгоритм. Фактически endpoint генерирует обычные персональные рекомендации.
- Метаданные TMDB хранятся бессрочно до явного удаления через кнопку обновления карточки или `DELETE /api/tmdb/metadata/:type/:id`.
